# 17 — Hosting decision for the owner-review build (stream C)

**Decision (integrator, 2026-09-14, owner asked for the easiest correct option):** host the owner-review application on **Railway** (railway.com) as one small always-on Node service with a persistent volume, under the owner's own Railway account. Label: `implemented` (project + GitHub deploy from `main`, `GET /health` HTTP 200 on 2026-09-15) — **not** `released`.

## Why Railway

| Need | Railway | Why not the alternatives |
|---|---|---|
| Runs Cursor's server unchanged (`node:http`, `npm start`, Node 22) | yes, auto-detected | Vercel/Netlify are serverless: no persistent disk for SQLite and the server would need a rewrite |
| Persistent disk for the dedicated SQLite file (`WEEKEND_DB_PATH`) | volume mounted at `/data` | a separate Postgres would add a vendor and an async rewrite of the store |
| Secrets outside Git | project variables in the Railway UI | same discipline as `.env.example` |
| Auto-deploy on every merge to `main` | GitHub integration | keeps the "continue the project" flow: merge = deploy |
| HTTPS URL to share with the owner | generated domain (custom domain later) | — |
| Separation from Kivo | separate account/project, separate store and keys | the Kivo Vercel/Supabase resources are not touched (AGENTS.md) |
| Cost | Hobby plan, about USD 5/month plus small usage | — |

## Code requirements for Cursor (issue #7, after the PR #14 fixes)

1. Bind to `0.0.0.0` and `process.env.PORT` when set (keep `127.0.0.1:8787` as the local default).
2. `GET /health` returning `HealthState` with HTTP 200 only when the store and configuration are OK (Railway health check path).
3. `WEEKEND_DB_PATH` may point into the volume (`/data/weekend.sqlite`); create parent directories at start.
4. Passcodes: accept `WEEKEND_OWNER_PASSCODE` and `WEEKEND_STAFF_PASSCODE` as plain values in the environment and hash them at start (scrypt, per the PR #14 review); the `_HASH` variants stay supported. Update `.env.example` accordingly.
5. `railway.json` (or `nixpacks.toml`) with the start command `npm start`, the health check path, restart policy, Node 22.
6. Serve the static UI from `src/ui/` on the same service (no second service).
7. Log only ids and counts; Railway keeps stdout logs.

Retention on the Railway volume (deadline plus at most one 10-minute idle sweep):

| Surface | What is stored | Retention |
|---|---|---|
| Photo bytes | in-memory only | 10 minutes / 32 entries |
| Cosmetic observations | SQLite `photo_observations` | 24 hours (`ret_photo_v1`) |
| Text preferences | SQLite `preferences` | 90 days after last activity (`ret_text_prefs_v1`) |
| Client address | HMAC-SHA256 digest in `sessions.client_key` (never the raw IP) | nulled after session expiry + 24 h (rolling, not a UTC-midnight boundary) |
| Guest upload counter | SQLite `guest_upload_quota` (client digest, day, count) | rows for past UTC days deleted by the idle sweep |
| Guest limiter counters | process memory only (`WindowCounter` / `AttemptLimiter`, keyed by the client digest, never the raw address) | rolling windows: 5 session creates / 10 min, 6 paid turns / min per client; passcode failures: 5 / 15 min per client, plus a process-wide backstop of 30 failures / 60 s across all clients (unkeyed) that also blocks a correct owner/staff passcode while tripped; all cleared on restart. |
| Guest sessions after the kill switch | SQLite `sessions` rows with `guest = 1` | `expires_at` is moved to the process-start time when `WEEKEND_PUBLIC_GUEST` is off, but that is defence in depth for the row itself, not what blocks the token: `requireSession` refuses every guest token with `session.guest_closed` whenever the switch is off, checked before expiry and independent of `expires_at`; `client_key` is nulled 24 h after that like any session; the row (and its dependents) is deleted 30 days after `expires_at` — see the session retention row below. |
| Session rows and dependents | SQLite `sessions`, `turns`, `allowed_actions`, `action_results`, `staff_handoffs`, `pending_requests`, plus `photo_observations`/`images` as a defensive backstop (normally already cleared by the 24 h photo-retention sweep) | deleted 30 days after `expires_at` (`SESSION_RETENTION_MS`), always after the 24 h client-key nulling. `subjects`, `preferences`, `permission_receipts` and `briefs` are not touched by this sweep — subject-scoped, kept independently (preferences on their own 90-day clock; consent receipts and approved briefs are meant to outlive the browser session). |

Deployment protection for the review period is the app's own passcode gate for staff/owner shells plus the unguessable Railway domain; no public launch is implied. `WEEKEND_PUBLIC_GUEST` defaults `true` in owner-review — `/try` opens a passcode-free customer session bounded by the C4 guest limits (session/turn/upload/spend-reserve) — and `false` in local; the value is read once at process start, so set it explicitly `false` in Railway Variables, deploy that change, and confirm the new deployment is live in the Deployments tab before treating the public chat as closed; saving the variable alone does not change the running process. Those guest limits key on the client address, so `WEEKEND_TRUST_PROXY=1` (variables table above) must stay set on Railway; without it every guest shares the proxy's address and one bucket. The domain, the project id and the account e-mail are therefore not written in this repository (it is public). They were published in this file between 2026-09-15 and 2026-09-18 and remain in Git history: the owner should regenerate the domain in Railway (Settings → Networking) and share the new one privately.
